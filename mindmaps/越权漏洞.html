# 越权漏洞 ## 产生原因 - 开发只做了登录校验，没做权限校验 - 认为"登录了就是合法用户" - 忽略了"合法用户之间数据应该隔离" - 信任前端传参 - userId / role 从请求参数中直接取 - 不从 Session/Token 中获取当前用户身份 - 前端隐藏代替后端校验 - 普通用户页面不显示管理入口 - 但管理接口 URL 可以直接访问 - 自增 ID 可预测 - 订单号 / 用户 ID 连续递增 - 攻击者改个数字就能遍历所有数据 - 代码能跑 ≠ 代码安全 - 越权没有语法错误，不会报错 - 接口正常返回 200，日志看不出异常 ## 原理 - 水平越权 - 绕过"数据归属"校验 - 同级别用户之间互相访问数据 - 用户 A 看到用户 B 的订单、个人信息 - 垂直越权 - 绕过"角色权限"校验 - 低权限用户访问高权限功能 - 普通用户执行管理员才能做的操作 - 与 SQL 注入 / XSS 的本质区别 - SQL 注入 / XSS 是攻击输入（注入恶意代码） - 越权是利用业务逻辑链条上的缺失环节 - 没有异常报错，接口正常返回 200 ## 水平越权（IDOR） - 核心手法：修改资源标识符访问他人数据 - 可篡改的参数 - 数字 ID（orderId=1001 → 1002） - 用户名（username=zhangsan → lisi） - 手机号 / 邮箱 / 身份证号 - UUID 也不绝对安全（可能泄露或可猜解） - 典型场景 - 查看他人订单详情 / 个人信息 / 聊天记录 - 修改密码功能（篡改请求中的 userId 改别人密码） - 文件下载（替换文件 ID 下载别人的文件） - 关键特征 - 接口正常返回 200 - 数据正常显示，只是不是你的 - 没有报错，日志看不出异常 ## 垂直越权 - 核心手法：低权限角色调用高权限接口 - 常见入口 - 直接访问管理后台 URL（前端只隐藏了菜单按钮） - 篡改 Cookie 中的角色字段（role=user → admin） - 未登录即可访问敏感接口（后端漏了校验） - API 接口只校验登录态，不校验角色权限 - 典型场景 - 普通用户增删改其他用户 - 查看全站数据（所有订单 / 所有用户列表） - 修改系统配置 / 执行敏感操作 - Pikachu 踩坑记录 - 登录只发 1 个包就失败 → Session 未建立 - 正确流程：先 GET 页面拿 PHPSESSID，再带 Cookie POST 登录 - POST Body 需包含 submit=登录 字段 ## 检测方法 - 白盒 - 审计接口的权限校验逻辑 - 检查是否同时具备"登录校验"和"角色校验" - 检查数据归属校验（user\_id == current\_user.id） - 关注只有 @login\_required 但没有 @role\_required 的接口 - 搜索从请求参数中取 userId / role 的代码 - 黑盒 - 准备：注册 2 个同权限账号（A / B）+ 1 个低权限账号（C） - 水平越权测试 - 账号 A 登录 → 访问自己的资源 → 记下响应 - 同一 Cookie 替换资源 ID 为账号 B 的 → 比较响应 - 如果返回了 B 的数据 → 水平越权确认 - 垂直越权测试 - 低权限账号 C 登录 → 直接访问高权限 URL / API - 低权限 Cookie 调管理接口 → 成功 → 垂直越权确认 - 工具 - Burp Suite（Repeater + Intruder 批量遍历 ID） - Autorize（Burp 插件，自动对比高低权限响应差异） - AuthMatrix（Burp 插件，多角色权限矩阵测试） ## 绕过手法 - 参数篡改 - 改 URL 路径：/user/info → /admin/user/list - 改 POST Body：role=user → role=admin - 改 Cookie：isAdmin=0 → isAdmin=1 - ID 枚举（水平越权核心） - 顺序遍历：id=1001,1002,1003... - 通过公开信息反查 ID（用户列表 / 响应中的其他接口泄露了 ID） - 接口重放 - 普通账号正常操作 → 抓包 → 替换 Cookie 为管理员 → 重放 - 对比不同权限 Cookie 的响应差异，判断哪些接口缺角色校验 - 未授权访问 - 不登录直接访问 URL → 后端没有强制登录校验 - 前端有页面跳转 / 弹窗拦截，但后端接口裸奔 ## 防御方案 - 水平越权防御 - 从 Session / Token 中取当前用户 ID，不信任前端传参 - 查数据后校验归属：`order.user\_id == current\_user.id` - 资源 ID 用 UUID 而非自增数字（增加猜解难度，辅助手段） - 垂直越权防御 - 每个接口做角色校验（不只校验登录态） - 中间件统一鉴权（@admin\_required 装饰器 / Spring Interceptor） - RBAC 权限模型（用户 → 角色 → 权限，三层映射） - 全局原则 - 默认拒绝：新接口先要求最高权限，再按需放开 - 权限最小化：用户只拥有完成任务所需的最小权限 - 服务端校验：前端隐藏菜单不叫安全措施，责任在后端 ## 越权与其他漏洞的组合 - 越权 + 文件下载 - 越权访问别人的文件下载链接 → 读他人文件（IDOR 打下载接口） - 越权 + XSS - 越权给管理员发含有 XSS payload 的消息 → 管理员触发 → 拿管理员 Cookie - 越权 + SQL 注入 - 越权访问管理后台 → 发现后台存在 SQL 注入 → 进一步利用 - 越权 + 文件上传 - 低权限用户越权调用文件上传接口 → 上传 webshell ## 实战靶场 - Pikachu — 水平越权 / 垂直越权模块 - DVWA — CSRF + 越权结合场景 - PortSwigger Web Security Academy — Access Control Labs - 挖洞实战关注点 - 涉及个人数据的接口（订单 / 地址 / 健康档案 / 聊天记录） - 管理后台的 API 路径（/admin/ / /manage/ / /api/admin/） - 密码修改 / 手机绑定等敏感操作的 userId 校验
